# 配图计划（自动模式）

用户给一篇文章（或课件、讲稿）要配图时，即使只指定其中一张，也按本文对照完整原文做 `plan.json`（单张可只含一项），用 `sb.py plan` 检查。新文章计划使用 v3，逐项保存全文核心内容的画／不画决定；旧 v1/v2 仍可读取。确认规则与 [SKILL.md](../SKILL.md) 第 2 步一致：默认把计划卡发给用户确认一次；用户说「直接出」或由自动流程调用时跳过，计划里写 `confirmed: skipped`。两种情况 `sb.py plan` 都会把计划卡存成 `<计划名>.plan-card.md`。

改写自 baoyu-skills baoyu-article-illustrator 的位置判定与大纲要求（MIT），改掉了它的四点：推荐时连风格一起换、关键词表粗糙、每次强制确认、没有作者记忆。

## 三层分工

- **样式与色彩**：一篇 / 一个系列内不变。
- **每张画什么**（人物场景、单幅隐喻还是结构图）：逐张按内容定。
- **结构与密度**：逐张按信息形状与要点数定。

## 第 1 步：定样式（每次写明理由，从不随机）

```bash
python3 scripts/sb.py style-for <场景> [--explicit C31] [--project 项目锁定.json]
```

优先级：本次用户明确指定 > 项目或系列锁定 > 作者档案（每个场景 2–3 个认可样式）> 出厂默认。作者档案里有备选时，按文章调性在认可的几个里挑，理由写进 `style.why`。场景 id 见 `scenes/scenes.json`（小红书 `xhs`、公众号配图 `wxillus`、公众号封面 `wxcover`、PPT `ppt`、信息图 `info` 等）。

## 第 2 步：找配图位置

先通读全文，列出 2–5 个核心论点。配图放在：

- **核心论点**（必须有）；
- **抽象概念**：读者需要一个画面才能抓住的概念；
- **数据对比**：数字之间的差别；
- **流程与步骤**。

判别要点（与独立复核员用同一份，源在 `scripts/stylebook/plan.py` 的 `PLANNING_RULES`）：

1. 值得配图的位置：核心论点、抽象概念、数据对比、流程与操作过程；纯装饰、泛泛的氛围图不配。
2. 先列出全文 2–5 个核心论点，以及结论或行动建议、最具体的操作过程；每项都要决定配图、已有视觉足够或文字足够，并写出针对该项的理由。不能只画一个例子就把其余核心机制视为已覆盖。
3. 一节通常只放一张，除非它有两个互不相干的要点。
4. 图放在一个意思讲完的那段之后：不紧跟总起句，也不紧跟悬念式设问；位置引用原文那一句，写成「……」之后。
5. 原文已有表格、清单、截图或作者供图时，逐项判断它是否真正回答读者的问题。已有视觉只覆盖字段、界面或局部步骤，不自动覆盖跨步骤关系、易错分叉、判断边界；新图若补出这些信息就保留，完全同义重复才删除。
6. 段落里有现成的同口径数据时，优先画数据，而不是氛围。比较前核对指标定义、分母、对象和时间范围；完播率与在看率等不同指标不是同口径，即使作者计算了倍数，也不能据此要求同一轴的倍数图或推断效果胜负。可保留明确标示口径差异的原表，或画指标区别；同一群体的独立指标仍可并列展示，但不能画成转化漏斗。
7. 要点与画面细节都忠于原文：不漏环节、不编数字；原文说「可选」「这次没做」的照写；场景的动作和情绪与原文一致。
8. 因果链原文没说首尾相接就不画成循环；只说“交易闭环”不足以证明末端会反馈到起点，须从原文另找循环依据。环节多于密度上限时合并相邻环节，不删环节。
9. 并列类别、分工用组成与网格，不把它们画成上下等级；作者推断不画成官方承认的事实。
10. 不把文中比喻按字面画出来；不画真实人物（名人、受访者、作者家人）的相似脸，用背影、剪影或标志性实物。
11. 同一类对比在一篇里用同一种结构。
12. 标题保留原文核心信息；改写不得改变对象、结论或行动。图中文字与要点保留读者理解机制或完成步骤所必需的条件，不用空泛标签代替具体内容。出图前逐字校对上图文案；text.items 是上图文字的权威清单，画面描述以图形与关系为主。subject 为说明位置而重复清单中完全一致的文字，属于可精简的提示词冗余，不据此否定内容或形式；若两处文字冲突、subject 要求清单之外的新文字，或冗余改变了画面含义，仍须拒绝并指出具体冲突。
13. 数字、费用、能力边界和效果声明须能在原文找到依据；不得把有条件的效果写成绝对保证。读完图应能理解这一段的核心判断，教程图应能知道下一步做什么。
14. 提交前把核心论点、关键机制、文末结论／行动建议和最具体操作逐项对照：已配图、现有视觉已解决同一阅读问题，或文字足够且图没有增益。遗漏有独立视觉增益的核心机制时补图；不得因张数已满或只见一张示例图就忽略它。

张数：尚未配图的公众号文章一般每个需要视觉帮助的核心论点一张，全文常见 3–7 张；不为凑数加图。文章已有配图时先核对图片文件确实存在、画面内容与正文相符，再判断是否解决同一阅读问题。若现有视觉和文字已覆盖所有核心项，v3 文章计划可以 `items: []`，但仍须逐项写 `coverage` 并通过独立 `plan-review`；不得仅凭 Markdown 图片引用或图片数量认定已覆盖。

## 第 3 步：每一处先判「信息形状」，再定表达形式

| 信息形状 `shape` | 表达形式 `form` | 可用结构 `structure` |
|---|---|---|
| 讲故事 `story` | 人物场景 `scene` | — |
| 观点 `opinion` | 单幅隐喻 `metaphor` | — |
| 步骤 `steps` | 结构图 `structure` | 流程 flow、时间线 timeline、旅程 journey、循环 cycle |
| 条件判断 `decision` | 结构图 | 条件分支图 decision-tree；判断条件与每条分支的动作或停止结果都要写进 `points` |
| 选项 `options` | 结构图 | 左右对比 compare、对比表 table、该做别做 dodont、天平 balance |
| 层级 `hierarchy` | 结构图 | 金字塔 pyramid、层叠 layers、树 tree、同心圆 nested、冰山 iceberg |
| 组成 `parts` | 结构图 | 卡片网格 grid、特性清单 features、清单 list、思维导图 mindmap |
| 多因 `causes` | 结构图 | 鱼骨 fishbone |
| 交集 `overlap` | 结构图 | 韦恩 venn |
| 两维排序 `two-axis` | 结构图 | 四象限 quadrant |
| 筛选 `filter` | 结构图 | 漏斗 funnel |
| 现状到目标 / 前后变化 `gap` | 结构图 | 桥接 bridge、左右对比 compare |
| 组合 `combination` | 结构图 | 等式 equation |
| 数据对比 `data` | 结构图 | 左右对比 compare、对比表 table、卡片网格 grid；随时间变化的数据用时间线 timeline |

每一处都写一句**依据句** `why`：为什么这里值得配图、为什么判成这个形状。例：「这一节先后讲了三步，读者要看到顺序，判为步骤 → 流程」。

形状的定义（同样与复核员共用，源在 `SHAPES[*].def`）：讲故事＝具体发生的事或一个人的经历（含真实人物的传记段）；观点＝作者的判断本身；步骤＝先后顺序或单向因果链；选项＝读者可以任选其一的方案；现状到目标＝从现状到目标，或已经发生的前后变化；数据对比＝同一口径的数字，定性差异不算；组成＝整体拆成并列几块，或几类人各自的做法、分工；筛选＝从多到少的漏斗，不是按身份对号入座。

## 第 4 步：密度与变化

- 结构图把要点逐条写进 `points`；密度由要点数决定：1–2 点稀疏、3–4 点均衡、5–8 点密集，并受格式上限约束（`formats/formats.json` 的 `density_max`；公众号文章配图最多均衡）。超了就拆成两张或精简。
- 人物场景和单幅隐喻也可写 `points`，记录图里不可丢失的原文事实；例如「手机里是父亲转来的育儿视频」，不能只写「许多不同视频」。这些事实会进入提示词和逐条看图核对。画面若不能可靠传达关键事实，换成结构图或保留原文截图，不用氛围图冒充信息图。
- 连续故事逐张写可见动作、角色和道具；「先查询再收到报告」等跨图关系在原文计划中保留，并对完整组另做顺序与连续性核对。单张的表格或报告图标不能证明前后因果；需要读者从单张理解的关键条件，须通过准确文字、箭头或其他明确表达呈现。
- 连续三张用同一结构时会提示复核原文关系；如果三段确实都是流程，可以保留。整组默认共用画风，用户明确指定的单张例外写 `manual: true`。

## 第 5 步：写计划并检查

新文章计划使用 v3：用原文路径和 SHA-256 固定内容版本，逐项记录全文覆盖决定；每张保留原文短引用。`points` 是画面必须表达的意思，`text.items` 是必须逐字写在图上的字。旧计划没有 `version` 时按 v1 继续读取。

```json
{
  "version": 3,
  "source": {"path": "article.md", "sha256": "<原文文件的 64 位 SHA-256>"},
  "scene": "wxillus",
  "style": {"code": "S01", "source": "author", "why": "作者档案：公众号配图默认暖白黏土"},
  "coverage": [
    {"claim": "专注与休息按顺序交替", "source_quote": "先专注再休息", "decision": "image", "image_ids": ["01"], "why": "三个步骤的顺序关系比逐句阅读更易在流程图中看清"}
  ],
  "items": [
    {
      "id": "01",
      "position": "§2「先专注再休息」之后",
      "source_quote": "先专注再休息",
      "shape": "steps", "form": "structure", "structure": "flow",
      "points": ["专注 25 分钟", "休息 5 分钟", "4 轮后长休息"],
      "what": "番茄钟的三步循环（给用户看的中文）",
      "subject": "the Pomodoro technique as three steps around a tomato timer（给编译器的英文）",
      "text": {"mode": "native", "items": [{"role": "title", "text": "番茄工作法"}, {"role": "label", "text": "专注25分钟"}]},
      "why": "这一节讲先后三个步骤，读者要看到顺序"
    }
  ]
}
```

`coverage` 对每个核心论点、关键机制、结论／行动建议和最具体操作写一项。`decision` 取 `image`、`existing_visual` 或 `text_sufficient`；选择新图须列出 `image_ids`，不画则写出已有视觉具体解决了什么阅读问题，或为什么文字足够。机器检查引用和映射，独立复核员再从原文重新盘点，不能把计划员的“不画”理由当成事实。`source.path` 相对计划文件所在目录解析。原文变动、引用不在原文、未知 `version` 都会在 `plan` 和 `batch` 入口拒绝；`plan-review --article` 传入的原文也必须是同一 SHA-256。新稿应填真实摘要值，不要照抄上面的占位符。

当 `items: []` 时，`plan` 只验证原文、样式和覆盖声明的结构；独立复核若发现必配漏项则不通过。即使复核通过，引用的旧图仍须人工或看图工具逐张核对实际画面；文本复核看不到图片像素。零新增图没有可生成的清单，不运行 `batch`，也不把它算作新出的一组图片。

可直接试编译的三类内容样例见 `examples/content-plan-v2/plan.json`：人物场景、带条件流程、双方案比较。样例只检验内容链路，不代表所用画风已正式准入。

- 画面里要出现的字逐字写进 `text.items`（标题不超过格式的字数上限），不要在 `subject`、`relations` 等画面描述里重复写上图标签；逐字查错后再生成。模型即使收到“只写指定文字”也可能把 `points` 或画面描述印上去，多标签或精确文字图优先试 `overlay`，导出后核对字与关系。`points` 是必须表达的意思，不保证都能靠图标读懂；如果文字必不可少，应列入 `text.items` 并为其安排可读空间。
- 流程图若含必须逐字保留的长命令，在该计划项的 `relations` 写明空间关系：小图标放在命令上方，命令占一条接近整行宽度的文字带，不把整张图固定分成「左图标、右文字」两列。导出后检查 390 px 手机宽度下命令是否完整、可读；若仍太小，改用精确叠字或拆图。此约束只给含长命令的图，不写入样式合同的所有流程题。
- 对角色或道具的**精确数量**有要求时，在每张计划项写非空的 `inventory`，例如 `"Exactly one fox sticker. No extra character, prop, letter or caption."`；计划生成清单时会原样传给编译器。逐张透明表情要显式选择 `"scene": "sticker", "format": "sticker-single"`，并在每张计划项附同一角色的 `references`（身份图从第二张起）。
- 出图前逐字复核 `text.items` 与 `points`：标题不能把原文主题换成别的说法；图上的步骤、条件和数字要能在原文定位。编译器将 `points` 送进生图提示词和看图验收要求；它们不自动变成图中文字。五个名词标签不足以替代教程中的操作方法。
- 用户手动指定某一张（换形式、换样式）时写 `"manual": true`，只影响那一张。
- 精确叠字图若在 `subject` 或 `relations` 指定无字底图，可另填 `final_subject` / `final_relations` 描述排字后的成品；生成仍使用底图描述，成品 QA 使用最终描述，并继续检查原文 `points` 与逐字文字。两项不填时沿用原描述。

```bash
python3 scripts/sb.py plan plan.json                     # 检查 + 打印确认表，并存成 plan.plan-card.md
python3 scripts/sb.py plan plan.json --manifests 清单目录  # 通过后生成每张图的编译清单（已预编译一遍）
python3 scripts/sb.py plan-review plan.json --article 原文.md  # 独立复核；必配漏项计入有效合理率
```

文章组在出图前执行 `plan-review`。若复核指出遗漏或错误，保留首版计划及复核报告，按原文修订后再复核；不能靠减少拟配图数量提高通过率。独立复核暂不可用时可继续试出图，但须标记“内容规划待复核”，不得把它称为已验收的文章完整组；**这条只适用于单独试做，不适用于写作 Skill 的正式发布流程——正式发布必须有通过的全文复核记录，复核不可用就停在发布前**。`plan` 的结构检查通过只说明数据能编译，不等于选图位置和图意已合格。

`plan-review` 默认通过 Coding Plan 的 `deepseek-v4.1-flash` 独立请求，把实际原文全文送入固定套餐端点。需要 `ARK_CODING_PLAN_BASE_URL` / `ARK_CODING_PLAN_API_KEY`，不切按量或其它模型。没有 Coding Plan 时可用 `--backend ark_agent_plan`（需 Agent Plan 的 Key）或 `--backend claude_cli`（本机已登录 Claude Code，无需 Ark Key）；三个后端的凭证、默认值和适用场景对照见 [backends.md「独立复核后端」](./backends.md)。结果中的 `_backend`、`_reviewer` 和 `_response_metadata` 保留实际后端、返回型号和响应。模型答了但缺项会点名重问一次，仍缺则连同原始回答一起报错；复核失败或服务不可用时停止，不能把结构校验通过当作独立复核通过。

## 第 6 步：确认一次，一口气做完

把确认表发给用户，一次确认，确认后在计划里写 `confirmed: user`。确认后逐张 `generate` → `qa` 验收 → 不合格单张返修（最多 2 次）。用户说「直接出」或由其他工具全自动调用时（如写作技能的自动流程），写 `confirmed: skipped` 直接出图，计划卡照样落盘、事后给表。`plan` 检查会拦下原文里找不到的数字、引语、英文专名，以及「一张图看懂」这类引导语。

## 记住用户的改动

本次改动只作用于本次计划；只有明确说“以后都这样”时才写长期偏好。主动、独立任务中重复出现的同一倾向可形成建议，但不能从单次出图失败或用户沉默推断审美偏好。偏好的存取入口以 `references/preferences.md` 为准。
